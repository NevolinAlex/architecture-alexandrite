# Собираемые логи

Компоненты источники логов:
* Shop API;
* CRM API;
* MES.

Список логов представлен в таблице ниже.

| Событие                                  | Поля                                                   |
|------------------------------------------|--------------------------------------------------------|
| Создан новый заказ                       | timestamp, userId, orderId                             |
| Загружен файл модели                     | timestamp, userId, orderId, fileId, fileName, fileSize |
| Заказ произведен                         | timestamp, userId, orderId                             |
| Произведен расчет стоимости изделия      | timestamp, orderId, fileId, calculatedCost, duration   |
| Заказ взят в работу оператором           | timestamp, operatorId, orderId                         |
| Открытие главной страницы MES оператором | timestamp, operatorId, duration                        |
| Заказ исполнен                           | timestamp, operatorId, orderId                         |
| Заказ передан в транспортную компанию    | timestamp, orderId, transportId                        |
| Заказ завершен                           | timestamp, orderId                                     |
| Сообщение направлено в очередь           | timestamp, orderId, messageId, messageSize             |

Дополнительное логирование: все ошибки возникшие в коде приложения должны логироваться с уровнем ERROR.

Все попытки несанкционированного доступа должны логироваться с уровнем WARN.

# Мотивация

Сейчас логирование вообще отсутствует как сущность, инциденты разбираются исключительно со слов пользователей системы:
пользователь описывает проблему, разработчик анализирует код и пытается найти проблему. В условиях отсутствия 
логирования процесс может занимать часы, в некоторых случаях дни, иногда из-за отсутствия дополнительных артефактов, 
таких как логи и метрики - локализовать проблему попросту может не представляться возможным.

## Метрики, на которые влияет внедрение логирования

* процент инцидентов без решения;
* длительность решения инцидентов;
* процент потерянных заказов.

# Предлагаемое решение

Стек технологий планируемый к внедрению:
* Fluentd - агент для сбора журналов логирования
* OpenSearch - хранилище логов;
* OpenSearch Dashboards - визуализация логов, анализ.


Архитектура решения:
* все приложения пишут логи в stdout в JSON-формате;
* Fluentd подключается к каждому экземпляру, построчно собирает события и направляет их в централизованный OpenSearch;
* OpenSearch раскладывает документы, индексирует и предоставляет к визуализации с использованием OpenSearch Dashboards;
* управление индексами, ротация, удаление индексов - этим управляет OpenSearch.

Схема с внедренными компонентами сбора логов находятся [здесь](jewerly_c4_model.drawio).

## Политика безопасности

* логи не должны содержать конфиденциальной/секретной/внутренней информации: допустимо передавать
  бизнес-идентификаторы;
* при работе с WEB-интерфейсом OpenSearch Dashboard обеспечить авторизацию с использованием протокола OAuth2 (по возможности интеграция по LDAP со службой доменных имен; при
  отсутствии регламент для администратора по созданию УЗ и матрицей полномочий), доступ к prod должен быть предоставлен:
    * администраторам системы;
    * РП;
    * разработчикам и QA - в результате согласования;
    * СТП.
* на стендах dev/release допустимо предоставлять доступ всем участникам проекта (команде разработки);
* обеспечить передачу данных между пользователем и компонентом по протоколу HTTPS c шифрованием данных по протоколу TLS 1.2+;
* доступ к WEB-интерфесу должен предоставляться с использованием корпоративного VPN или из внутренней сети компании.

## Политика хранения

Индексы ротируются в OpenSearch с использованием ISM (Index State Management):
* по достижении TTL индексы целиком переносятся в холодное хранилище (требуется предусмотреть как SSD так и HDD);
* по достижении TTL2 индексы удаляются;
* политика создания индексов - индекс на 1 месяц, c учетом политики хранения.

Требования к хранению представлены в таблице ниже.

| Индекс                    | Компоненты                 | TTL warm | TTL cold | Обоснование                                                                                                                           |
|---------------------------|----------------------------|----------|----------|---------------------------------------------------------------------------------------------------------------------------------------|
| services_*_{month}_{year} | shop-api, mes-api, crm-api | 90 дней  | 90 дней  | 90 дней требуется для разбора ситуаций с заказами, исполнение заказов может длиться месяцами. </br>Прогнозируемый объем 50ГБ в месяц. |

# Анализ логов

Предлагаемый алертинг:
* % ошибок в логах превышает 10% за 5 минут;
* время открытия главной страницы оператором > 5000ms & > 5 раз за 5 минут;
* произошла ошибка при любом событии связанном с заказом;
* резкий рост заказ от АПИ за час: количество заказов за час превышает 500% от пикового за последние 7 дней.
