# Анализ

Трейсинг предлагается вводить с момента создания заказа, для получения общей информации о задержках и зависаниях
на каждом статусе бизнес-процесса.

В первую очередь требуется локализовать текущие проблемы пользователей.
Пользователи сталкиваются с задержками после оформления заказов т.е. в момент когда они уже ожидают, что заказ взят
в работу компанией, а значит допустимо рассматривать места задержек только после статуса MANUFACTURING_APPROVED.

## Выявление мест зависания заказов

Перечень мест где может происходить зависание по процессу исполнения заказа, созданного в интернет-магазине:

1. Время между созданием заказа и подтверждением заказа системой: SUBMITTED → PRICE_CALCULATED → MANUFACTURING_APPROVED.
2. Передача заказа из CRM в MES - переход между статусами MANUFACTURING_APPROVED и MANUFACTURING_STARTED.
3. Задержки в производстве по готовности заказа - переход между статусами MANUFACTURING_STARTED и
   MANUFACTURING_COMPLETED.
4. Задержки подготовки заказа и отправке клиенту: MANUFACTURING_COMPLETED → PACKAGING → SHIPPED.
5. Задержки в работе транспортной компании: SHIPPED → CLOSED.

Так же при создании заказа через АПИ требуется в трейсинге учесть связь при передаче заказа от MES до CRM.

## Перечень данных для трейсинга

| Поле          | Описание                                         |
|---------------|--------------------------------------------------|
| trace_id      | Идентификатор цепочки                            |
| span_id       | Идентификатор шага                               |
| order_id      | Идентификатор заказа в системе                   |
| timestamp     | Дата и время выполнения шага в utc               |
| status        | Статус выполнения шага (OK, ERROR)               |
| service_name  | Сервис в котором случился шаг                    |
| error_message | Причина ошибки, если статус завершился с ошибкой |
| shipping_id   | Идентификатор заказа в транспортной компании     |
| user_id       | Идентификатор пользователя совершившего заказ    |
| mes_id        | Идентификатор задачи на расчет стоимости заказа  |
| messages_id   | Массив идентификаторов сообщений в MQ            |
| status_id     | Идентификатор статуса шага                       |

Некоторые параметры заполняются только в рамках определенных шагов.

# Мотивация

От устойчивости и производительности работы данных процессов зависит прибыль и репутация компании.
Внедрение трейсинга запросов позволит искать узкие места в бизнес-процессе или работе ПО и оптимизировать их.

Ближайшая задача, решаемая трейсингом - поиск задержек в процессе исполнения заказов, созданных как через интернет
магазин, так и через АПИ.

В дальнейшем поможет локализовывать и устранять проблемы подобного рода, при возникновении новых бизнес-процессов.
Трейсинг запросов в таком случае должен вводиться одновременно с реализацией бизнес процесса, это
позволит своевременно локализовывать и устранять их при обнаружении.

Бизнес-технические метрики, которые позволит улучшить внедрение трейсинга:

* скорость локализации проблем при выполнении заказов;
* процент задержанных заказов;
* процент потерянных заказов;
* процент успешных заказов;
* время перехода из статуса в статус - к каждому должны быть предъявлены требования;
* процент недобросовестных исполнителей - оператор, завод, транспортная компания.

# Предлагаемое решение

Внедрить трейсинг на уровне приложений. В качестве решения использовать OpenTelemetry.

1. На уровне сервисов произвести внедрение SDK. В соответствии с проведенным анализом произвести внедрение трейсинга в
   точки смены статусов в соответствии с бизнес процессом исполнения заказа. Доработки требуется внести во все сервисы
   системы:
    * shop-api;
    * mes-api;
    * crm-api.
2. Развернуть СУБД для хранения трейсов ClickHouse.
3. Произвести развертывание и настройку компонентов для сбора и визуализации трейсов:
    * развернуть OpenTelementry connector;
    * развернуть Jaeger;
    * подключить Jaeger к ClickHouse;
    * произвести проверку работоспособности связки.
4. Настроить приложения на передаче событий в коллектор.

Схема с внедренными компонентами для трейсинга размещается по [пути](jewerly_c4_model.drawio).

# Компромиссы

Внедрения трейсинга - работа, требующая не малого количества ресурсных вложений (деньги, люди).
Требуется провести оценку работ в человеко-днях и определить стоимость и время работ.
При этом потребуется менять приоритеты существующих работ, в случае если не планируется активно развивать
бизнес-процессы в течении ближайших пол года или год, допустимо произвести ручной анализ текущих проблем через
добавление дополнительных логов, а анализ текущих проблем "произвести в лоб" - это может оказаться дешевле, такую
работу так же требуется оценить.

Альтернативные варианты решения решения текущих проблем бизнеса:

* внедрение мониторинга критических показателей - лаги очередей, ошибки обработки;
* внедрение логирования дополнительных сообщений/ошибок и ежедневный их ручной анализ.

# Безопасность решения

Требования к безопасности решения трассировки:

* события трассировки не должны содержать конфиденциальной/секретной/внутренней информации: допустимо передавать
  бизнес-идентификаторы;
* при работе с WEB-интерфейсом Jaeger обеспечить авторизацию с использованием протокола OAuth2 (по возможности интеграция по LDAP со службой доменных имен; при
  отсутствии регламент для администратора по созданию УЗ и матрицей полномочий), доступ к prod должен быть предоставлен:
    * администраторам системы;
    * РП;
    * СТП.
* обеспечить передачу данных по протоколу HTTPS c шифрованием данных по протоколу TLS 1.2+;
* доступ к WEB-интерфесу должен предоставляться с использованием корпоративного VPN или из внутренней сети компании.
